# BE_M2_AUTH_SURFACE — Auth surface (Marine.Participant.Mobile): Keycloak-unified OTP / social / password login for the mobile participant

> **Repo:** `addesso-project` (Identity module + `Bff/src/Marine.Participant.Mobile` + `infrastructure/keycloak`). **Goal of M2:** give the mobile app every login flow it already calls, all ending in a **real Keycloak session** for the `inktavia-mobile` client — so the M1 BFF (which validates `inktavia-realm` JWTs, audience `marine-mobile-bff`) accepts them and `GET /api/v1/mobile/me` returns 200 with role `mobile_user`.
>
> **Confirmed architecture decisions (do NOT re-litigate):** (1) **Keycloak-unify** — the mobile participant joins the same Keycloak model as provider/admin; the BFF trusts Keycloak, not local Aizen-JWT. (2) **Role = Participant/Consumer** — `WorkshopRoleContext.Participant`, realm role `mobile_user` (+ `customer_user` where the existing consumer stack uses it). "Owner" is product-language only; no new Identity role.
>
> **The core reuse principle:** the participant OTP-login, provisioning, and password-recovery verticals are built by **mirroring the Provider/Admin variants that already exist** (the Admin variant was itself a mirror of Provider — follow that precedent exactly). Google/Apple **id_token validation already exists** in `OAuthProviderClient` (real Google/Apple JWKS, Apple client-secret JWT, PKCE/nonce) — **reuse its validation**, but route provisioning to **Keycloak** instead of the local-JWT path. Do NOT invent new crypto or a second ticket system.
>
> **Scope fence:** touch **Identity** (new participant auth verticals), **`infrastructure/keycloak`** (new flow + client binding, additive), and the **mobile BFF Auth feature**. **Do NOT touch** `MarineProvider`, `AdminPanel`, provider-web, admin-web, CargoDry, or the existing Provider/Admin OTP-login/password-recovery code — they are the reference and must stay **byte-for-byte**. Additive only; existing consumer local-JWT endpoints (`api/v1/auth/*`, participant OAuth) stay working (they are superseded for mobile but not deleted in M2).

M2 decomposes into five slices (each can be executed and reported independently, mirroring the Admin OTP handoff split): **M2a** Identity participant OTP-login · **M2b** Keycloak participant flow binding · **M2c** BFF OTP endpoints (+ native ticket→session handoff) · **M2d** BFF+Identity Google/Apple · **M2e** BFF password register/login/recovery/refresh/logout.

**Identity — the variants to mirror** (`Modules/Identity/src`; note historical namespace `Aizen.Modules.InktaviaStore.*`):

Domain services `ProviderOtpLoginDomainService`/`AdminOtpLoginDomainService : I*OtpLoginDomainService` (`RequestAsync`/`VerifyOtpAsync`/`ResendAsync`). Admin passes clientId `"admin-panel"`, provider `"provider-portal"`.
- Ticket service (SHARED, reuse as-is): `IProviderOtpLoginTicketService` → `MintAsync(string keycloakSubjectId, string clientId, CancellationToken)` (HMAC-SHA256 with `OtpLoginTicketOptions.Secret`, single-use jti in Redis, TTL 120s), `ConsumeAsync(string jti, …)`. Options `OtpLoginTicketOptions` (`"OtpLoginTicket"`: `Secret`,`ConsumeSecret`,`TtlSeconds`,`KeycloakAuthorizeBaseUrl`,`SpaRedirectUri`), `OtpLoginOptions` (`"OtpLogin"`: `OtpLength=6`,`OtpTtlSeconds=300`,`ResendCooldownSeconds=60`,`MaxAttempts=5`,`MaxRequestsPerIdentifierPerWindow=5`,`IdentifierWindowSeconds=3600`).
- Provisioning: `OrganizerKeycloakProvisioningDomainService : IOrganizerKeycloakProvisioningDomainService` (`ProvisionAsync` — find-by-sub → find-by-email → link → `UserEntity.CreateFromKeycloak(...)`, ensure `RoleNames.Organizer` + one `WorkshopRoleContext.Organizer` profile + onboarding row) and its **Admin mirror** `AdminKeycloakProvisioningDomainService`. Profile-by-subject resolvers: `GetOrganizerProfileByKeycloakSubjectQuery/Handler` → `IUserProfileRepository.GetOrganizerProfileByKeycloakSubjectAsync` → `OrganizerProfileDetailDto`; generic `GetUserByKeycloakSubjectQuery` → `UserBySubjectDto{UserId,KeycloakSubjectId}` (`GET /api/v1/identity/users/by-subject/{sub}`).
- Password recovery: `ProviderPasswordRecoveryController` (`api/v1/identity/auth/provider-password-recovery`: `request`/`verify-otp`/`reset`/`resend-otp`), `ProviderPasswordRecoveryDomainService`, crypto/rate-limit helper `PasswordRecoverySecurity` (static PBKDF2 100k/SHA256, `GenerateNumericOtp`,`GenerateOpaqueToken`,`Hash`,`Verify`,`MaskEmail`,`MaskPhone`), `PasswordRecoveryOptions`, Keycloak password op `IIdentityKeycloakPasswordService.ResetPasswordAsync(subject,newPassword)` + `RevokeSessionsAsync`.
- **Existing social (reuse its validation only):** `IOAuthProviderClient`/`OAuthProviderClient` — `ValidateIdTokenAsync(provider, idToken, expectedNonce, ct)` (Google `oauth2/v3/certs`, Apple `appleid.apple.com/auth/keys`, Apple client-secret JWT, nonce/aud/iss), `GetAuthorizeUrl`, `ExchangeAsync`; `OAuthOptions` (`"OAuth:Google/Apple"`); entities `UserExternalLoginEntity` (`ProviderUserId = id_token.sub`), `LoginType.Google/Apple`. Existing consumer social controller `RegistrationController` (`participant/oauth/start`,`participant/oauth/callback/{provider}`) mints **local** tokens — that is the OLD path; M2 keeps the validation, changes the sink to Keycloak.

**BFF — the Auth façade to mirror** (`Bff/src/MarineProvider`):
- `RegisterProviderCommandHandler`: `IProviderKeycloakAdminClient.FindUserByEmailAsync`→`CreateUserAsync`→ `IIdentityRemoteCall.ProvisionFromKeycloak(...)`→`SetUserAttributeAsync("provider_profile_id",…)`→`AssignRealmRoleAsync(ProviderPendingRole)`→`SendVerifyEmailAsync`. `EnsureProviderProfileCommandHandler` (social first-login): `GetOrganizerProfileByKeycloakSubject`→ provision if unlinked.
- `IProviderKeycloakAdminClient`: `FindUserByEmailAsync`,`GetUserByIdAsync`,`CreateUserAsync(CreateKeycloakUserRequest)`,`SetUserAttributeAsync`,`AssignRealmRoleAsync`,`SendVerifyEmailAsync`; `IProviderKeycloakServiceTokenProvider.GetAccessTokenAsync` (client_credentials for the confidential BFF client). The mobile BFF already has `IParticipantKeycloakServiceTokenProvider` (M1); it must gain a `IMarineMobileKeycloakAdminClient` (deferred in M1).
- OTP-login BFF slice: `OtpLoginController` (`request`/`verify`/`resend`), handlers delegate to `IIdentityRemoteCall.RequestProviderOtpLogin`/`VerifyProviderOtpLogin`; verify maps `data.LoginTicket` through. Password: `PasswordRecoveryController` (`forgot`/`otp/verify`/`reset`/`otp/resend`).

**Keycloak** (`infrastructure/keycloak`):
- SPI `provider-otp-login-ticket` (`ProviderOtpLoginAuthenticator`): reads `login_ticket` from authorize, verifies HMAC with `ticketSecret`, checks `clientId==allowedClientId` + exp, POSTs `{jti}` to `identityBaseUrl+consumePath` with `X-Otp-Login-Consume-Secret`, then `setUser(sub)+success()` — **Keycloak issues the tokens**. Config: `identityBaseUrl`,`consumePath`,`ticketSecret`,`consumeSecret`,`allowedClientId`,`maxSkewSeconds=30`.

- `inktavia-realm-realm.json`: `inktavia-mobile` = public, `standardFlowEnabled=true`, **`directAccessGrantsEnabled=false`**, redirects `inktavia://auth/callback`,`com.inktavia.mobile://auth/callback`,`http://localhost:19006/auth/callback`; realm `verifyEmail=false`, `resetPasswordAllowed=true`; **no client has ROPC enabled**; roles `mobile_user`,`customer_user` exist; seed user `mobile.user@inktavia.com` = `mobile_user`.

## 1. Deliverables

### M2a — Identity: Participant OTP-login vertical (mirror Provider/Admin exactly)
- `ParticipantOtpLoginController` `[Route("api/v1/identity/auth/participant-otp-login")]`, `[Authorize(Policy="IdentityWrite")]`: `POST request`/`verify`/`resend` + `POST consume-ticket` (`[AllowAnonymous]`, `[FromHeader("X-Otp-Login-Consume-Secret")]` guard). Reuse the shared `RequestProviderOtpLoginRequest`/`VerifyProviderOtpLoginRequest`/`ResendProviderOtpLoginRequest`/`ConsumeTicketRequest` DTOs (the admin controller reuses them too).
- `ParticipantOtpLoginDomainService : IParticipantOtpLoginDomainService` (mirror `ProviderOtpLoginDomainService`) — resolve the user, require `KeycloakSubjectId` non-empty **and** an active `WorkshopRoleContext.Participant` profile (`_profileRepo.GetActiveProfileIdAsync(user.Id, WorkshopRoleContext.Participant)`); anti-enumeration synthetic result on miss; PBKDF2 OTP; persist `ParticipantOtpLoginRequestEntity` (+ EF migration); dispatch via the reused `IProviderOtpLoginNotifier`. On verify success mint with **clientId `"inktavia-mobile"`**: `_ticketService.MintAsync(record.KeycloakSubjectId, "inktavia-mobile", ct)`. Reuse `IProviderOtpLoginTicketService`, `OtpLoginOptions`, `PasswordRecoverySecurity` — **do NOT create a second ticket service or notifier.**
- Register `IParticipantOtpLoginDomainService → ParticipantOtpLoginDomainService` in the same DI method that registers provider/admin. New DTOs (`RequestParticipantOtpLoginRequest`/…/`VerifyParticipantOtpLoginResponse`) only if the shared provider DTOs don't fit; prefer reuse.

### M2b — Keycloak: participant OTP-login browser flow + bind to `inktavia-mobile` (mirror the admin init.sh block, additive)
- In `init.sh`, add a **"Participant OTP Login browser"** flow (copy the browser flow, add `provider=provider-otp-login-ticket` execution ALTERNATIVE at top), config alias `participant-otp-login-config` with `identityBaseUrl=http://identity-api:8080`, `consumePath=/api/v1/identity/auth/participant-otp-login/consume-ticket`, `ticketSecret=$OTP_LOGIN_TICKET_SECRET`, `consumeSecret=$OTP_LOGIN_CONSUME_SECRET`, `allowedClientId=inktavia-mobile`, `maxSkewSeconds=30`; idempotently bind `inktavia-mobile` `authenticationFlowBindingOverrides.browser` to it.
- Ensure the **`marine-mobile-bff` audience mapper** exists on `inktavia-mobile` (from `BE_M1_FOUNDATION_KICKOFF.md §1.9`) and the seed `mobile.user@inktavia.com` keeps role `mobile_user`. The SPI jar is already mounted — no jar change.

### M2c — BFF: mobile OTP endpoints + **native ticket→session handoff** (the client already calls these live)
- `POST /mobile/auth/otp/send { phone }` → `RequestParticipantOtpLoginCommand` → `IIdentityRemoteCall.RequestParticipantOtpLogin({ channel:"sms", identifier: phone })`; anti-enumeration message passthrough.
- `POST /mobile/auth/otp/verify { phone, code }` → `VerifyParticipantOtpLoginCommand` → Identity verify → obtain `loginTicket` → **complete the Keycloak handoff server-side** (see §2.1) → return `{ data: { accessToken, refreshToken, expiresIn, tokenType } }` (the client reads `response.data.data`). This is the key divergence from provider/admin: mobile is native, so the BFF (not a browser SPA) drives the ticket→session exchange and returns tokens directly.
- Add the BFF `IMarineMobileKeycloakAdminClient` (mirror `IProviderKeycloakAdminClient`) now — M2d/M2e need it.

### M2d — BFF + Identity: Google / Apple (reuse OAuthProviderClient validation, provision to Keycloak)
- `POST /mobile/auth/google { idToken }` and `POST /mobile/auth/apple { identityToken, fullName }` → BFF → a **new Identity endpoint** `POST /api/v1/identity/auth/participant-social-login` that: validates the native id_token via the existing `IOAuthProviderClient` (add a `ValidateNativeIdTokenAsync(provider, idToken, nonce?)` variant — native SDK tokens have `aud = the mobile OAuth client id` and may carry no server nonce; validate iss/aud/exp/signature, and the client nonce only if present — see §2.2); find-or-create the **Keycloak** user (via BFF `IMarineMobileKeycloakAdminClient` or an Identity-side Keycloak admin op — mirror `RegisterProviderCommandHandler`'s create+link), link the Participant profile (`ProvisionParticipantFromKeycloak`, a new `ParticipantKeycloakProvisioningDomainService` mirroring the Organizer one), persist `UserExternalLoginEntity` (`LoginType.Google/Apple`, `ProviderUserId = sub`), assign role `mobile_user`; then mint a ticket for `inktavia-mobile` and complete the handoff (§2.1) → return `{ data: { accessToken, refreshToken, … } }`.
- Also create the profile-by-subject resolver `GetParticipantProfileByKeycloakSubjectQuery/Handler` (+ `IUserProfileRepository.GetParticipantProfileByKeycloakSubjectAsync`) mirroring the Organizer resolver — needed for social first-login and by M3's runtime profile re-check.

### M2e — BFF: password register / login / recovery / refresh / logout
- `POST /auth/register { email, password, fullName, phone }` → mirror `RegisterProviderCommandHandler`: `FindUserByEmailAsync`→`CreateUserAsync`→ Identity `ProvisionParticipantFromKeycloak`→`SetUserAttributeAsync("participant_profile_id",…)`→`AssignRealmRoleAsync("mobile_user")`→`SendVerifyEmailAsync`. Return `{ data: { … } }` after completing a session (or a "verify email" next-action per §2.3).
- `POST /auth/login { email, password }` → **no ROPC is enabled anywhere** (§2.3): default = the BFF performs `grant_type=password` **server-side** against the confidential `marine-mobile-bff` client (enable `directAccessGrantsEnabled` on `marine-mobile-bff` only — a confidential, BFF-only client, so credentials never leave the BFF), yielding a user session for `mobile_user`. Map Keycloak errors to the client envelope.
- `POST /auth/forgot-password`+`/verify-otp`+`/set-new-password` → mirror `ProviderPasswordRecoveryController`/`ProviderPasswordRecoveryDomainService` as a **participant variant** (`ParticipantPasswordRecoveryController` `api/v1/identity/auth/participant-password-recovery` + `ParticipantPasswordRecoveryDomainService`), reusing `PasswordRecoverySecurity` + `IIdentityKeycloakPasswordService.ResetPasswordAsync`. BFF proxies.
- `POST /auth/refresh` → BFF calls Keycloak token endpoint `grant_type=refresh_token` (client `marine-mobile-bff`) → new tokens. `POST /auth/logout` → BFF calls Keycloak end-session / token revoke for the refresh token.

## 2. Config / flags to confirm (do not hardcode) — three real mechanism decisions

### 2.1 Native ticket→session handoff (default vs alternative)
The provider/admin ticket is consumed by a **browser** hitting Keycloak `authorize?...&login_ticket=…`. Mobile is native — the BFF must complete it server-side.
> **Default:** the BFF runs the OIDC **authorization-code + PKCE** flow itself against `inktavia-mobile`: generate `code_verifier/challenge` + `state` + `nonce`, `GET {KeycloakAuthorizeBaseUrl}/authorize?client_id=inktavia-mobile&response_type=code&redirect_uri=<BFF-registered>&code_challenge=…&login_ticket=<ticket>` (SPI logs the user in), capture the `code` from the redirect to a **BFF-registered redirect_uri** (add e.g. `http://localhost:17003/auth/callback` + the deployed BFF origin to `inktavia-mobile` redirectUris), then `POST /token grant_type=authorization_code` (client auth = `marine-mobile-bff` confidential secret + `code_verifier`) → tokens. Reuses the existing SPI unchanged.
> **Alternative (only if approved):** Keycloak **token-exchange** (`urn:ietf:params:oauth:grant-type:token-exchange`, impersonation) by the confidential `marine-mobile-bff` for the resolved subject — fewer round-trips but a preview feature needing realm config. Pick one; record the choice in the report.

### 2.2 Native Google/Apple id_token validation
Native SDK id_tokens differ from the server-redirect flow (`aud` = the Google iOS/Web or Apple client id; often no server-issued nonce).
> **Default:** add `IOAuthProviderClient.ValidateNativeIdTokenAsync(provider, idToken, nonce?)` that reuses the existing JWKS fetch + signature/iss/exp checks, accepts `aud ∈ {configured native client ids}` (add `OAuth:Google:NativeAudiences[]`, `OAuth:Apple:NativeAudiences[]`), and validates a client-supplied `nonce` only when present. Never accept an unsigned or `aud`-mismatched token. Confirm the Google iOS/Web client IDs and the Apple service/bundle id from the mobile app config; **never hardcode or log secrets.**

### 2.3 Password grant + email verification
> **Default:** enable `directAccessGrantsEnabled=true` on the **confidential `marine-mobile-bff`** client ONLY (not on public `inktavia-mobile`); the BFF alone does the password grant. Document the security note (ROPC stays server-side, behind the confidential client + rate limiter). **Register** returns a session directly if `verifyEmail=false` (realm seed) — confirm whether mobile should enforce email verification (`SendVerifyEmailAsync` + a `verify_email_required` next-action) or allow immediate login. Reconcile the client's realm string (`KEYCLOAK_REALM=inktavia` in the app env) with the real `inktavia-realm`.

Other flags: `OTP_LOGIN_TICKET_SECRET`/`OTP_LOGIN_CONSUME_SECRET` shared with provider/admin (already in compose/init); `KEYCLOAK_MARINE_MOBILE_BFF_CLIENT_SECRET`; SMS channel for participant OTP (confirm the SMS provider the notifier uses vs the dev `[DEV-ONLY]` log line).

## 3. Acceptance / verification (must all pass)
1. **OTP:** `POST /mobile/auth/otp/send { "phone":"+90…" }` → 200 anti-enumeration; Identity log shows `[DEV-ONLY] participant OTP … NNNNNN`. `POST /mobile/auth/otp/verify { phone, code }` → 200 `{ data: { accessToken, refreshToken, expiresIn, tokenType } }`; the access token is a **Keycloak** `inktavia-mobile` token with `aud` including `marine-mobile-bff` and realm role `mobile_user`.
2. **Handoff proof:** feeding that access token to `GET /api/v1/mobile/me` (M1) → 200 with `roles:["mobile_user",…]` (proves the ticket→session exchange produced a BFF-valid Keycloak token, not a local JWT).
3. **Google/Apple:** `POST /mobile/auth/google { idToken:<native> }` and `POST /mobile/auth/apple { identityToken, fullName }` → 200 tokens; a first-time login creates+links a Keycloak user + Participant profile (`UserExternalLoginEntity` row, `mobile_user` assigned); a repeat login re-uses it (idempotent). Invalid/expired/`aud`-mismatched id_token → 401, no user created.
4. **Password:** `POST /auth/register` (new email) → user created in Keycloak + Participant profile linked + `mobile_user`; `POST /auth/login { email, password }` → 200 tokens (mobile_user). `POST /auth/forgot-password`→`/verify-otp`→`/set-new-password` resets the Keycloak password and revokes sessions; the new password logs in, the old fails.
5. **Refresh/logout:** `POST /auth/refresh { refreshToken }` → fresh tokens; `POST /auth/logout` invalidates the refresh token (subsequent refresh → 401).
6. **Untouched:** `git status` shows changes only under Identity (new participant auth files + migration), `infrastructure/keycloak/init.sh` + realm JSON, and `Bff/src/Marine.Participant.Mobile/`. Provider/Admin OTP-login, password-recovery, provider-web, admin-web, CargoDry are git-clean. Existing consumer `api/v1/auth/*` + participant OAuth endpoints still respond (not deleted).
7. **Build:** Identity + mobile BFF build 0 errors (run on a machine with the .NET 9 SDK — the Cowork sandbox has none).
