**Date**: 2026-06-14  
**Scope**: Stable ID strategy and cross-module reference manifest for admin-demo dataset

---

## 1. Problem Statement

The Identity, Vessel, and ServiceRequest modules run as separate microservices with separate PostgreSQL databases. They cannot query each other's databases during seeding. Cross-module relationships (e.g. Vessel referencing an Identity user) must use stable, pre-defined IDs.

All entity primary keys are `long` with PostgreSQL `GENERATED BY DEFAULT AS IDENTITY`. Since the column is `BY DEFAULT` (not `ALWAYS`), EF Core/PostgreSQL allows explicit value insertion without the `OVERRIDING SYSTEM VALUE` clause.

## 7. Idempotency

Every seeder checks `AnyAsync(e => e.Id == model.Id)` before inserting. Re-running any service startup will not duplicate records.

---

## 8. Risks / Follow-ups

- **ID Conflict Risk**: If real production data is somehow migrated to the same database and auto-generated IDs collide with the 10001-99999 range before sequences are advanced, there could be conflicts. The seeder's idempotency check prevents duplicate inserts but cannot prevent accidental ID overlap if sequences weren't advanced on the first run.
- **Cross-service startup order**: Identity should ideally seed before Vessel and ServiceRequest to ensure referenced UserIds exist. However, since Vessel/ServiceRequest don't validate Identity FK at DB level (no cross-DB FK), startup order is not enforced.
- **Sequence advancement**: The seeder advances sequences to 100000 after seed. If the database is recreated, sequences reset to 1 and mock IDs in 10001+ range will work correctly.
